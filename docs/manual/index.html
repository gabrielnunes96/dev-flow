Manual do dev-flow

Da demanda em texto ao PR com pipeline verde, com você aprovando cada etapa.

O dev-flow é um conjunto de plugins do Claude Code que transforma o jeito de trabalhar do time em processo repetível: especificar, desenhar, planejar, implementar tarefa a tarefa com testes, revisar, validar no ambiente e abrir o PR. Você aprova as decisões; o resto segue sozinho.

/fluxo:tecnicaTécnicaDesenho no código real, arquitetura e ameaças
/fluxo:planoPlanoTarefas pequenas, verificáveis e em ordem

Instalação

Claude Code, Cursor (Team Marketplace / Third-Party Imports) ou vendor com Agent Skills. Depois instala o núcleo e um plugin por stack.

  1. Claude Code — marketplace

    Caminho local ou URL git.

    claude plugin marketplace add <caminho-ou-url-do-dev-flow>
  2. Instale o núcleo

    Sempre. Traz as skills do processo, os agentes, os hooks e os scripts.

    claude plugin install fluxo@dev-flow
  3. Instale as stacks e o CI do projeto

    Stack X no perfil → plugin stack-X. Use o montador abaixo para gerar os comandos.

  4. Cursor

    Team Marketplace: importar o repo (.cursor-plugin/marketplace.json). Ou Third-Party Imports + plugins Claude. Ou vendor:

    python -I scripts/exportar_skills.py --destino <projeto>/.agents/dev-flow --plugins fluxo,stack-python
  5. Mantenha atualizado

    Claude: claude plugin marketplace update dev-flow. Depois de mudar manifests Claude no repo: python -I scripts/sincronizar_hosts.py.

i

Para o time inteiro de uma vez: declare o marketplace e os plugins no .claude/settings.json versionado do projeto (Claude) ou use o Team Marketplace do Cursor. O montador abaixo também gera o trecho Claude.

        Começar
        
Configurar um projeto

        
Abra o Claude Code na pasta do projeto (pode estar vazia) e rode /fluxo:iniciar. Ele lê o que dá para ler e pergunta só o que é seu.

        

          
O que ele detecta sozinho

            
  • Stacks pelos arquivos: *.csproj, package.json, pyproject.toml, pom.xml, go.mod, Dockerfile, *.tf, manifestos Kubernetes, drivers de banco.
    • 
            
  • Comandos de build, teste, lint e vulnerabilidades.
    • 
            
  • Provedor de CI pelos arquivos de pipeline.
    • 
            
  • Nuvem e onde a aplicação roda.
    • 
            
  • Branch padrão e código gerado (candidato a proteção).

          
O que ele pergunta

            
  • Rastreador: local ou Azure Boards.
    • 
            
  • Onde guardar as especificações (versionadas ou locais).
    • 
            
  • Como validar: URL, token, VPN, dados de teste.
    • 
            
  • O que nunca pode ser tocado.

        

        
O que ele grava

        Trabalhar
        
Ciclo de uma demanda

        
Tudo de uma vez com /fluxo:entregar e a demanda em texto livre, ou etapa por etapa. Cada etapa produz um arquivo em {docs}/{slug}/, então o trabalho sobrevive a sessões novas.

        

          
EtapaComandoGeraQuem participaVocê

          
            
Funcional/fluxo:demanda01-funcional.md: regras (RN), requisitos (RF), critérios de aceite (CA) em Dado/Quando/Então, fora de escopo, dúvidas—Responde até 4 perguntas por rodada e aprova

            
Técnica/fluxo:tecnica02-tecnica.md: componentes, contratos antes/depois, dados, segurança, testes por CA, riscos, implantação, CI/CD; ADRsanalista por repositório; arquiteto se há decisão estrutural; seguranca se há superfície de ataqueDecide custo, prazo e produto; aprova

            
Plano/fluxo:planotarefas.json + 03-plano.md: uma tarefa = um commit = uma entrega verificávelCards no Boards, se configuradoAprova a ordem e o corte

            
Tarefas/fluxo:task todasCódigo, testes, cards/{id}.html, um commit por tarefatestador, revisor, seguranca, validador, depuradorAutoriza cada commit

            
PR/fluxo:prpr.md e o PR aberto depois do seu pushSkill do CI para acompanhar a pipelineFaz o push e o merge

          

        
◆
As aprovações são suas. Nada é implementado antes de funcional, técnica e plano aprovados. A aprovação fica registrada no topo de cada documento (“aprovada em dd/mm/aaaa”). Entre uma aprovação e outra, o fluxo segue sem pedir confirmação.

        
Como escrever uma boa demanda

        
Explique o problema e para quem, não a solução. Diga o que é sucesso, o que fica de fora e qualquer restrição de prazo ou volume. Exemplo:

        
Os analistas precisam exportar os chargebacks do mês em CSV para conciliar com o banco. Hoje copiam da tela. Precisa respeitar o filtro de loja e não pode passar de 50 mil linhas por arquivo.
O fluxo pergunta o que falta (colunas, formato de data, permissão) e transforma em critérios verificáveis.

      


      

        Trabalhar
        
Ciclo da tarefa

        
/fluxo:task pega a próxima tarefa pronta (ou /fluxo:task T3, ou todas) e percorre os mesmos passos sempre.

        
    
          
  1. Pré-condições
    Perfil válido, árvore git limpa, token renovado se houver, skill de cada stack carregada (stack X → stack-X:X).
    2. 
          
  2. Abrir a tarefa
    plano.py proxima escolhe a pronta (dependências feitas, não protegida); estado vira “andamento” (e no Boards também).
    3. 
          
  3. Pensar antes de codar
    Pré-condição, pós-condição e invariante de cada unidade que muda; casos de borda que se aplicam. É daí que saem os testes.
    4. 
          
  4. Implementar
    Pela skill da stack e pelas convenções do projeto, copiando a operação existente mais parecida. Nada de regra que a funcional não pediu.
    5. 
          
  5. Testar
    Cada critério com pelo menos um teste que falharia sem a mudança. Regra combinatória → testador desenha a matriz.
    6. 
          
  6. Revisar
    revisor sempre; seguranca em paralelo quando o diff toca auth, dados pessoais, pagamento, upload, segredo ou infraestrutura. Achado crítico bloqueia o commit.
    7. 
          
  7. Validar no ambiente
    validador conforme validacao.tipo: lote HTTP, script SQL aplicado e revertido, comando, ou tela no navegador.
    8. 
          
  8. Commitar com permissão
    Stage só dos arquivos da tarefa, e para. Commit depois do seu “pode commitar”. Nunca push.
    9. 
          
  9. Registrar e seguir
    tarefas.json marcado como feito com o hash, card salvo (e publicado no Boards), próxima tarefa.
    10. 
        

        
■
O ciclo para e pergunta quando: falta acesso ao ambiente, uma falha não tem causa clara, a regra é ambígua, algo sai do escopo, ou acontece um item de pare_e_pergunte do perfil.

        
Com pressa: tarefas em paralelo

        
plano.py prontas lista as tarefas que não dependem entre si. Peça “faz as prontas em paralelo” e cada uma vai para um subagente em worktree isolada; os commits voltam na ordem do plano.

      


      

        Trabalhar
        
Corrigir bugs pela causa raiz

        
/fluxo:depurar com a mensagem de erro ou a descrição. A regra: primeiro um teste que falha, depois a correção.

        

          
1 · Registrar e reproduzir
Sintoma literal em bug.md, o menor comando que mostra o erro. Sem reprodução não há correção, só palpite.

          
2 · Investigar por hipóteses
O depurador lista 2 a 4 hipóteses, testa da mais barata para a mais cara, usa git bisect quando há versão boa.

          
3 · Provar e corrigir
Teste de regressão que falha, correção mínima na causa, revisor, validador e commit com permissão.

        

        
■
Bug em produção com impacto? Mitigar vem antes de corrigir: rollback, feature flag ou desligar o job. Essa decisão é sua, e o fluxo pergunta antes.

CI/CD

        
Defina ci.provedor no perfil e instale o plugin correspondente. Os três seguem as mesmas regras: os comandos do perfil (o que passa local passa no CI), segredo só no cofre do provedor, produção com aprovação manual.

        

          
Azure PipelinesGitHub ActionsGitLab CI

          
            
Plugin / skillazure-pipelines:pipelinegithub-actions:actionsgitlab-ci:gitlab

            
Modelosdotnet, front/node, python, java, go, sql, docker, terraform, deploy por estágiosci (matriz por stack), docker (GHCR + Trivy), deploy por environmentgitlab-ci (verificação, testes, SAST, imagem, deploy)

            
SegredosVariable groups / Key VaultSecrets do environment + OIDCVariáveis protegidas e mascaradas + OIDC

            
Aprovação em produçãoApprovals no environmentRequired reviewers no environmentwhen: manual + ambiente protegido

            
Diagnósticoaz pipelines runs showgh run view --log-failedglab ci trace

          

        
◆
Criar pipeline, secret ou environment e reexecutar uma execução são ações visíveis para o time: o fluxo prepara tudo e pede o seu “sim”. A aprovação de produção é configurada por você na interface do provedor, não no YAML.

Regra escrita em texto o modelo pode esquecer. As proteções abaixo são aplicadas pelo hook guard, que roda antes de cada ferramenta e bloqueia de verdade.

Além do hook, são regras do processo: commit só com o seu “pode commitar”, terraform apply e deploy em produção nunca pela sessão, validação de banco só em base de desenvolvimento.

      


      

        Referência
        
Método de raciocínio

        
Implementar, revisar, testar e depurar seguem o mesmo método, escrito em plugins/fluxo/referencias/raciocinio.md. A qualidade não depende de o modelo lembrar de pensar nisso.

        

          
Modelar antes de mexer
Entrada, transformação e saída numa frase. Onde há estado e quem mais escreve nele. Onde estão as fronteiras de confiança.

          
Contrato de cada unidade
Pré-condição, pós-condição, invariante e o que acontece no erro. O que não se consegue escrever vira critério faltando.

          
Casos de borda
Cardinalidade (0, 1, muitos, máximo+1), ausência, números, texto, tempo e fuso, ordem, concorrência, falha parcial, dependência fora, permissão, volume.

          
Custo
O() do caminho principal; I/O vence CPU; N+1, laço aninhado e tudo em memória são os suspeitos. Otimizar só com número na mão.

          
Execução simulada
Caminho feliz, uma borda e um erro percorridos na cabeça com os valores. Diferença do esperado é bug antes de existir.

          
Sem overengineering
O menor código que atende os critérios, no padrão do projeto. Abstração, camada, cache, fila ou dependência só com requisito escrito. Teste: se eu apagar isto, qual critério falha?

          
Depurar por hipóteses
Reproduzir, observar o literal, listar hipóteses, derrubar a mais barata primeiro, causa raiz, teste que prova.

        

        
◆
Antes de dizer “pronto”: cada critério tem um teste que falharia se o critério quebrasse; build, lint e testes verdes nesta execução; validação feita ou registrada como pendente; e dito o que não foi verificado.

        Ajuda
        
Problemas comuns

        
O hook diz “Projeto sem .claude/projeto.json”
Rode /fluxo:iniciar na raiz do projeto. Sem perfil, só a proteção de segredos no commit vale.

        
“perfil.py validar” aponta erro
A mensagem diz o campo e os valores aceitos (ex.: ci.provedor: 'jenkins' inválido). Avisos não bloqueiam; erros bloqueiam o ciclo da tarefa.

        
O guard bloqueou uma ação que eu queria
Ele está aplicando o perfil. Se a regra estiver errada, ajuste protecao no .claude/projeto.json; se o bloqueio for git push, faça o push você mesmo no terminal.

        
A skill da stack não carregou
Confira se o plugin stack-X está instalado (claude plugin install stack-X@dev-flow) e se X está em stacks do perfil. Sem o plugin, o ciclo segue com as convenções do projeto e avisa no fechamento.

        
A validação diz “SEM ACESSO: token não gerado (VPN?)”
O script de token saiu com código 2. Conecte a VPN e peça “valida a T3 de novo”. A tarefa fica registrada como não validada até lá.

        
Fiz uma mudança no marketplace e o projeto não viu
Claude: claude plugin marketplace update dev-flow e sessão nova. Cursor Team Marketplace: Refresh. Vendor: rode de novo exportar_skills.py. Skills e hooks carregam no início da sessão.

        
Quero uma stack que não existe
Use "outra" em stacks por enquanto e veja docs/novo-plugin-de-stack.md: um plugin pequeno com uma skill de três partes, registrado no schema e no marketplace. O teste test_marketplace.py confere a estrutura.

Glossário

        

          
            
ADRRegistro de decisão de arquitetura: contexto, decisão, alternativas e consequências.

            
AgenteEspecialista que roda em contexto isolado e devolve um resumo.

            
CA-nCritério de aceite verificável, em Dado/Quando/Então.

            
CardDescrição final de uma tarefa: implementação, testes, validação. Vai para o Boards quando configurado.

            
GuardHook que bloqueia ações proibidas pelo perfil antes de acontecerem.

            
HookCódigo executado pelo Claude Code em eventos (início de sessão, antes de uma ferramenta). É garantia, não sugestão.

            
Perfil.claude/projeto.json: o contrato entre o processo genérico e o projeto.

            
Ponto de aprovaçãoEtapa em que o fluxo para e só avança com o seu “ok”: funcional, técnica e plano.

            
SkillProcedimento carregado sob demanda quando o pedido combina com a descrição dela.

            
SlugNome curto em kebab-case da demanda; nome da pasta dos documentos.

            
STRIDERoteiro de ameaças: falsificação, adulteração, repúdio, vazamento, negação de serviço, elevação de privilégio.

            
Tarefa prontaA fazer, não protegida e com todas as dependências feitas.
